# Effect implementation

The CLI, programmatic entrypoint and repository helpers share the Effect implementation in this directory. The executable is `dist/cli.js`; `index.ts` also exposes the program and its Promise boundary for embedding.

## Exercise the implementation

Package discovery uses the source checkout's `pnpm-workspace.yaml` declarations over Git-visible files, including declared nested locations and exclusions. Materialized workspaces are not canonical package sources. The resulting catalog supplies dependency resolution and discovery checks; Watch uses the same declarations to observe newly added manifests. Registry selection still controls which packages are installed.

Workspace-owned settings are declared once in `initialization.ts`; both ownership checks and the initial `.gitignore` are derived from that policy. `file-policy.ts` classifies runtime environment files, examples and caches for copying, observation and snapshots. Each operation retains its own preservation and exclusion rules. Environment-related TypeScript filenames are ordinary source, not runtime env files.

From the repository root:

```sh
pnpm --filter create-next-hydra build
pnpm --filter create-next-hydra test
pnpm --filter create-next-hydra exec node tests/run-example.ts conditional
pnpm --filter create-next-hydra exec node tests/run-example.ts bindings
pnpm --filter create-next-hydra exec node tests/run-example.ts application
pnpm --filter create-next-hydra exec node tests/run-example.ts editorial --install
```

The example runner copies the selected authored folder into a temporary checkout, invokes the **built executable** with `compose <name> --no-install`, prints the materialized output, and removes that temporary copy on exit. `application` first explains its layout without creating application files or a receipt. It then initializes its `enhanced-site` definition, changes its copied canonical template, verifies that Check fails without refreshing files or state, refreshes in another CLI process, shows a Diff for a local edit, and verifies a subsequent invocation refuses to overwrite that edit. Other examples initialize `editorial-site`; use `editorial` for the smallest example. These commands do not change the authored examples or the repository's named workspaces.

For a packaging check, build and pack this package, install that tarball into an unrelated directory, then run:

```sh
pnpm --filter create-next-hydra exec node tests/run-package.ts /absolute/path/to/installation/node_modules/create-next-hydra
```

This uses only the installed executable and workers. Disposable copies of the authored examples exercise creation, dependency installation, typecheck/build/runtime execution from the installed application root, rendered-source linting, Explain/Diff, local-edit protection and programmatic Add. The harness removes its example copies; remove your separate tarball installation when finished. It does not use real credentials or provision external services.

The optional `--install` on the example runner exercises default pnpm installation and a second-process refresh, checking that the normalized lockfile survives. It can download dependencies; use the files-only examples when network/package-store access is unavailable. The CLI itself accepts `compose <name>` or `compose --all`, with `--no-install`, `--offline`, `--copy-env`, `--check`, `--diff`, `--watch`, and `--explain [file]`. Targeted Explain takes a single workspace name.

### Add to an existing project

The CLI supports `add <reference>`, with `--yes` / `-y` and `--overwrite` / `-o`. Run it from the project root. References may be local item JSON files, URLs or configured registry references.

`Workspaces.existing({ root })` binds a project without reading or changing it. `inspectAdd({ reference })` reports file and package changes, compatibility assumptions and an opaque precondition. `add({ reference, overwrite, expected? })` checks the request again, compares any supplied precondition, and rechecks observed project files before calling ShadCN with retained artifacts. CLI prompts finish before mutation starts; `--yes` alone never approves replacing files or dependency versions. Declining or cancelling leaves the project unchanged.

ShadCN writes into the actual project, not a replacement workspace. After it finishes, Hydra rereads manifests and merges package-local requirements without losing native edits. Copied package manifests and root package-manager configuration count as installation inputs, even without top-level dependency declarations in the registry item. Every explicit dependency-bearing invocation reconciles installation again, even when declarations match. A failed native operation, manifest merge or dependency install can leave changes; the error identifies that phase and does not claim rollback. Inspect the files before retrying.

Addition has no project lock, break-lock option, ownership receipt or composition snapshot. Its scoped temporary storage contains transport artifacts only. Concurrent additions are not serialized, and the pre-installation check does not freeze editors. Provider bindings, known provider requirements and required/forbidden slots are checked against the existing application; unknown compatibility requirements are disclosed. Native ShadCN environment additions are disclosed by key only, never value. Addition does not re-render templates, switch providers or fabricate a root ShadCN configuration for CSS/font/config changes.

### Select multiple workspaces

`compose --all` discovers Git-visible `workspaces/<name>/next-hydra.json` definitions once at startup, including untracked definitions that are not ignored. Tracked definitions remain selected even when an ignore rule matches; deleted definitions are excluded. Discovery does not parse the definitions, so one unfinished edit does not prevent selection of the others.

One-shot Sync, Check, Diff and Explain process each selected workspace independently and sequentially. A typed failure is reported with its workspace name; the command continues through the remaining names and then exits unsuccessfully with the failed names. Defects and interruption are not downgraded to ordinary workspace failures. Interactive lock recovery remains sequential; no simultaneous prompts are introduced.

`compose --all --watch` consumes all selected workspace streams concurrently, each using its own ordinary Watch/Sync loop. A slow installation or refresh failure in one does not stall the others. A fatal observer failure ends the invocation and joins sibling cleanup. Newly added workspace names require restarting the command; edits to already selected definitions remain observed.

### Watch canonical source

Run `compose <name> --watch` to synchronize canonical source. Use `--no-install` for files-only iteration or `--copy-env` for explicit initial local environment copying. Watch is mutually exclusive with Check, Explain and Diff. It does not start a development server; run the application's Turbo tasks in another terminal.

Observation connects before initial Sync. A capacity-one pending signal retains saves during synchronization; subsequent attempts use a fixed 50 ms batching window and re-read current source. Writes and installation stay serialized through the same Sync operation. Each attempt reports one result. Ordinary refresh failures leave observation active but do not schedule retries without another source event. Defects and interruption preserve the full Effect cause, including when cleanup also produces a typed failure. Observation failure ends the session and joins active-operation cleanup. Cancellation closes subscriptions and uses Sync's existing release rules.

Once the initial environment-copy phase completes, subsequent attempts preserve environment files even if installation failed afterward. Watch never seeds env examples or copies later credential edits. Existing locks are reported as refresh failures, not broken by a background watcher; stop Watch and run one-shot Compose for interactive lock recovery.

Observation connects recursively beneath the source checkout, pruning materialized output and known caches and filtering runtime env events. Each attempt accepts conservative discovery events before reading its definition or source. Normal preparation returns the exact consulted inputs, selected whole-package directories and registry-governed exclusions. Before publishing files or installing dependencies, Watch connects that coverage. If preparation discovers a new external input, Watch re-runs preparation with observation connected before using the output. The event filter then narrows to the prepared inputs. A failed preparation leaves discovery broad so missing-source and definition repairs remain observable. An installation failure still retains the successfully prepared coverage. Checkout observation remains connected, and filter updates do not queue artificial refreshes.

The exact named definition, registry.json files, package manifests and canonical `.gitignore` files remain discovery inputs. New eligible files in selected packages trigger refreshes; unselected governed files do not. SourceInventory asks Git for visible paths, so ignored additions do not trigger idle refreshes. Already captured explicit inputs remain observable even if ignored. Git's resolved index and common-directory `info/exclude` are observed separately: tracking an ignored file or changing repository exclusions can add/remove output without a source edit. Worktree index paths are supported. Only the required metadata paths and their ancestors are watched, not Git object/reference trees.

External ignore files and Git configuration changes are observed too. Git supplies global/system config locations and expands configured paths; included config files remain observable even when missing or empty. With no `core.excludesFile`, the standard XDG/home ignore location is observed. Changing the configured path replaces the metadata subscriptions through Effect `ScopedRef`, while checkout observation stays connected. Missing parent directories are observed from an existing ancestor with unrelated trees pruned. Config changes only refresh output when selected Git visibility changes; unrelated settings do not manufacture a synchronization.

Watch's platform-specific config discovery uses `git var` from Git 2.42 or newer. Registry/package discovery remains conservative. Local registry artifacts captured by preparation are observed, including paths outside the checkout; their last-known subscriptions remain active when preparation fails, so deletion and restoration can recover. An external path never successfully acquired is not known to observation: repair it and save the definition or restart Watch. The fixed batching window does not wait for a quiet period under continued saves. Remote registries are not polled.

`SourceChanges` is the scoped observation boundary. It lazily loads `@parcel/watcher` when Watch starts, awaits native subscription readiness through Effect acquire/release, buffers invalidations in an Effect queue and awaits unsubscribe on scope exit. Parcel owns recursive discovery and directory tracking; there is no application-managed per-directory listener table. The source checkout is the stable watch root, so replacing an application/package directory beneath it remains observable. Restart Watch if the checkout root itself is moved or replaced. The lifecycle adapts Effect's earlier Parcel adapter with its MIT notice retained. Linux behavior is exercised; exact OS event delivery, Windows and network filesystem behavior are not established.

### Locate source before editing

From a source checkout containing a workspace definition:

```sh
node packages/create-next-hydra/dist/cli.js compose storefront-contentstack --explain 'apps/web/app/[locale]/layout.tsx'
```

Prefer a targeted explanation. It reports a canonical source or template path and its registry owner. Templates also show selected module references, slots and their binding order. Whole-package files point at their canonical package paths; files constructed by built-in composition policy are labeled as such instead of inventing a copy source. Source attribution is not a promise of byte-identical copying: manifest, alias and hostname policies still apply. An explicitly requested existing workspace setting points at that workspace's own file, not a shared default that Sync omits. Without a file, Explain lists the selected managed-file origins; it does not scan local output for edits or list every workspace-owned setting.

Explain prepares the current definition using the same captured inputs and scoped staging as Sync, including the external registry adapter. It does not publish application files, acquire a destination write lease, install dependencies, copy credentials or read/repair the receipt. It remains useful before initialization and when local output is edited or receipt data is broken. This is a source-location report, not a claim about the applied composition, installation readiness or a stable live output tree. A changed definition or captured source fails the explanation rather than returning mixed selection information. Unknown/unselected paths are errors; local drafts and runtime environment files are not assigned invented ownership. Temporary preparation may still require filesystem and process access.

### Inspect freshness without synchronizing

Use `compose <name> --check` to inspect an initialized workspace. Check compares the current prepared output with recorded ownership and actual file bytes/modes, checks intended output paths for collisions, and evaluates the recorded installation against current inputs and output markers. Unrelated local files do not affect readiness. Its service result separates file findings from dependency readiness; the command exits unsuccessfully when attention is required.

Initialization and Check inspect declared workspace settings directly, without walking unrelated local output. The full unregistered-file inventory belongs to Diff, which requires access to the directories it inspects.

File findings distinguish creates, updates, removals, ownership-record changes, local conflicts, unregistered files occupying intended targets and missing initialization settings. `record` means the ownership/fingerprint record needs reconciliation even when the file bytes already match; `setting` means a missing root `.gitignore`, not permission to replace an authored setting. Check never adopts matching unowned files. It does not write application files, update the receipt, seed settings, copy credentials or run pnpm—even with `--copy-env` or `--no-install`. Like Explain, preparing the current source still uses scoped staging and the registry adapter.

The read guard rejects an existing write lock and verifies the receipt remains unchanged after inspection. A completed concurrent synchronization invalidates the result. Missing state reports an uninitialized workspace; invalid state and unresolved operations return typed errors, without repairs. This does not freeze editors or prevent a file changing immediately after inspection. Check and Explain are mutually exclusive; neither creates a snapshot.

Check does not probe the pnpm executable selected by the current shell: a version probe can bootstrap/download it. It checks the recorded installation, current Node/platform/options and bounded filesystem evidence instead. Sync additionally verifies the pnpm version before reuse. Opaque installation inputs, such as lifecycle hooks or detected external pnpm configuration, conservatively report reconciliation required even after a prior successful install; their freshness cannot be proved from the recorded manifests. A successful install and a reusable installation are different facts.

### Inspect local edits against a saved composition

`compose <name> --diff` compares owned application files with the Composition Snapshot selected by the receipt. It reports a patch, unregistered file paths and file/directory blockers, plus saved source attribution for changed files. That attribution belongs to the selected snapshot, not today's registry, and remains useful when current preparation fails. The bound service exposes the reusable lazy Effect `workspace.diff`. Diff does not prepare current sources or read the workspace definition, so it remains available with a broken definition. It does not prove freshness; Check answers that different question. Check, Explain and Diff are mutually exclusive command modes.

After Sync finishes its requested dependency step—including an explicit skip—it captures verified owned bytes in a private bare Git store at `<source>/.cache/workspace-snapshots/<workspace-key>.git`. The key identifies the destination path. It pins the immutable commit, rechecks the live files against their applied fingerprints, then publishes the commit reference in the existing receipt. Identical trees reuse the prior commit when available. Earlier and unpublished commits remain pinned; automatic history pruning is not implemented. Fresh applications get neither this store nor a receipt.

The receipt, not Git HEAD or the newest commit, selects the baseline. Applied ownership and successful installation evidence remain independent. If files apply but installation fails, or an intervening edit prevents snapshot publication, Diff keeps using the previous baseline and flags an incomplete synchronization. Its patch may include tool-applied changes, not only developer edits. Stopped pending file operations can be inspected without resolving their intent; an existing write lock still blocks inspection. Newly owned files are additions, not unregistered drafts. Tool-owned pending replacement files are not labeled as drafts.

Snapshot capture excludes runtime env files, known credential paths and runtime/cache output. Unregistered files are listed by path and never added to snapshot history. Diff copies only eligible owned observations into disposable storage, with its own index and object writes; it does not stage the live workspace or persist edited bytes in the saved Git store. Git configuration and inherited index/object locations are isolated, application attributes cannot normalize captured bytes, and external diff/text-conversion helpers are disabled. Text patches represent Git's file modes, not every OS permission bit. Local Git commands finish before their temporary storage is released.

Absent ownership, invalid state and unavailable snapshot objects produce distinct errors without resets or adoption. A later explicit Sync may recreate missing snapshot storage only after normal ownership/conflict checks. Diff checks for a writer and changed receipt but does not freeze uncoordinated editors. Lock recovery follows the policy below; it does not bypass unresolved file or installation state.

### Recover a retained lock

Compose exclusively creates `.workspace-composition.lock` through Effect FileSystem before writing. A readable `owner.json` identifies the operation, PID and start time. Effect finalizers remove the lock after ordinary completion or joined cancellation, unless incomplete publication or installer evidence requires retaining it. A hard crash can leave the directory behind.

An existing lock always blocks a new Sync. Run the same `compose <name>` command in an interactive terminal; it asks you to stop other Compose commands before approving recovery, defaulting to No. Approval moves the lock and its evidence to `.workspace-composition.recovery/<id>/`, then retries under a new lock. It does not ask you to delete anything manually. Declining, cancelling or running without an interactive terminal leaves the lock untouched. The inspected owner, receipt and retained publication are rechecked before breaking. There is no force flag or implicit approval through generic confirmation skipping.

Breaking a lock does not kill a process, prove an installer stopped, accept incomplete files or reset ownership. Those independent checks may still block the retry. Check and Diff never prompt for or perform recovery. Successful Sync reports the archive location alongside its ordinary result. Ordinary validated file/install recovery after the lock is released still needs no confirmation.

This is a local, single-user guard against two terminals writing the same workspace. It uses only Effect FileSystem, with no database, heartbeat, expiry or PID-liveness probing. Owner metadata is diagnostic, not proof that a process stopped. Explicit recovery assumes other Compose commands have stopped; observation checks are not an atomic takeover protocol. Filesystem tests use the same implementation in memory, and real-process coverage runs on Linux. Windows, shared/network filesystem and power-loss guarantees are not established.

### Resume a stopped file update

An explicit `compose <name>` can reconcile a stopped file update after its writer has released the lock. No separate recovery flag is needed. Before preparing current source, Sync validates the complete persisted intent and observes every recorded path, including unchanged files. Exact after-state matches establish completed transitions; exact before-state matches retain previous ownership. A changed definition or template is then prepared normally, without replaying obsolete staging.

Recovery removes only recorded temporary replacements whose bytes and mode match their intended after state. It checks the whole operation before cleanup and rechecks observations before revision-guarded publication. A post-failure edit, deletion, changed mode, partial temporary file, or malformed journal blocks recovery without adopting those bytes. Filesystem mutation is joined before the lock is released. Ordinary editor races remain possible; this is not a filesystem-wide transaction.

Recovered ownership clears successful-install evidence and leaves the existing snapshot selected. Dependency reconciliation follows the normal install/skip policy, and only a completed Sync publishes a new snapshot. Check rejects pending intent; Diff stays read-only. Initialization follows the bounded rules below. Unpublished receipt candidates are retained on authorized lock breaking, never automatically selected as authoritative state.

### Resume initialization

Named initialization records each settings/env target as planned, started or completed. The started record precedes the write; the write and completed record finish together before interruption releases the lease. Only target paths and progress are recorded, never credential values, source paths or fingerprints. Fresh project creation remains receipt-free.

- Planned means this invocation never started that file. Recovery leaves any existing workspace-owned file alone and replans missing files.
- Completed means creation finished, not that the CLI owns its current contents. Subsequent edits and permissions remain untouched, and recovery does not read credential contents.
- Started without completion is ambiguous if the target exists. Recovery reports its path and preserves it, even if it appears complete. After inspection, move the suspect file to a private backup location before retrying. If the target is absent, the next Sync can replan without assuming it was created.

The retry uses current sources and current options. An earlier `--copy-env` request is not replayed automatically. Pass it again to copy missing local files; a files-only retry without it does not create env files. Examples remain documentation and never seed runtime values. Missing root ignore settings are initialized normally. Initialization targets are validated against the permitted settings/env paths and may not overlap managed source, state or cache files.

A failed completion-record publication preserves incomplete evidence; a retained receipt candidate also retains the lock. Existing files cannot substitute for missing completion evidence. The same file-conflict and snapshot-publication rules apply after initialization recovery.

### Resume after an interrupted installation

The installer records confirmed process-group completion in the receipt before releasing the write lease. If stopping the process or recording that fact fails, the lock remains. An empty lock directory or elapsed time alone is not evidence that another process has stopped.

A subsequent explicit Sync can recover a recorded stopped attempt only when every owned file still matches its applied bytes and mode, including the lockfile. An interrupted lockfile rewrite is ambiguous, not automatically accepted as pnpm normalization. Changed or missing files produce a conflict without overwriting them or removing installed output.

Recovery clears the incomplete attempt and earlier successful-install evidence, retaining ownership and the previous snapshot. Sync then prepares current sources and follows the requested install policy: default installation retries pnpm; `--no-install` leaves dependencies pending. Recovery itself does not run an installer, publish readiness or automatically repeat lifecycle scripts. Check remains read-only and rejects unresolved intent; Diff does not clear it.

The examples are ordinary folders containing manifests, registries, modules, and templates. Test setup reads these files; it does not construct an application out of strings. The explicitly fake `.env.local` example checks that local credentials are excluded from package output.

Focused behavior tests execute the real workspace, source-borrowing, and composition services over a stateful in-memory `FileSystem` Layer, with controlled inventory and external registry adapters. They inspect resulting files and typed failures, not helper calls or invocation order. Loading authored input files uses disk; composition execution in these tests does not invoke Git or ShadCN processes. A bounded successful Git process adapter lets unrelated filesystem/dependency cases pass the capture boundary; it does not emulate object storage or validate snapshot contents. Real Git tests cover snapshot publication, baseline authority, patches, exact bytes and index isolation. These adapters are not a production virtual filesystem or a mount for Node APIs.

Disk integration tests use scoped copies of the same examples and the real installed ShadCN. They cover exact-file installation, included registries, qualified references, transitive package files, template rendering, conditional/nested recipes, opaque assets, patch declarations, authored workspace settings, source changes, destination conflicts, and write failures. Git visibility checks exercise the resulting ignore rules through Git, not string assertions against the configuration. The environment command test uses an isolated Git repository and worktree with explicitly fake credentials to verify ignored-file discovery, checkout precedence and primary-worktree fallback. Separate worker tests cover interruption, retained staging, and private diagnostics. Temporary storage remains necessary at this boundary because upstream ShadCN and its worker use the real filesystem.

## Boundaries

- `Workspaces` constructs lazy handles and orchestrates source preparation, destination writes, explicit environment copying, dependency reconciliation and snapshot publication. `fresh().materialize()` requires an empty destination and retains no ownership receipt. `named().sync()` initializes or refreshes under one write lease through installer completion and snapshot publication. `named().explain(target?)` returns current source attribution without destination writes or receipt access. `named().check()` reports freshness through shared file and dependency observers; `named().diff` compares observed owned files with the saved snapshot without preparation.
- `WorkspaceState.withWrite()` owns the destination lock and the `.workspace-composition.json` codec and transitions. Callback-scoped access records and completes file/install attempts, brackets initialization writes with durable progress, reconstructs ownership from complete verified recovery observations and publishes a snapshot at an expected revision; callers cannot save arbitrary receipts. `withRead()` shares the decoder, refuses a writer, and checks the receipt did not change during inspection without creating a lock. Diff explicitly allows validated incomplete intent; Check does not. One receipt holds ownership, metadata revision, applied-file revision, successful-install evidence, the active snapshot reference and any pending operation.
- `SourceChanges.open()` acquires ready observation and returns buffered invalidations plus replaceable coverage. `named().watch()` owns batching and runs the existing synchronization operation. A supervised collector retains notifications while Sync or terminal reporting is busy; no second composer, generic scheduler or application supervisor is introduced.
- `WorkspaceSnapshots` owns private Git capture, retention and comparison. It receives detached, eligible bytes; Workspaces coordinates live-file verification and receipt publication through WorkspaceFiles/WorkspaceState. It never chooses the baseline from a Git ref. Its Layer uses the platform filesystem and process services, not a generic command-runner framework.
- `WorkspaceDependencies.reconcile()` derives installation inputs from complete prepared manifests, workspace/lockfile configuration and declared patch targets. It verifies the applied inputs, invokes pnpm through Effect's process service, checks outputs and records success. `inspect()` supplies the read-only input/output comparison used by both Check and reconciliation. `recover()` verifies a recorded stopped attempt against all applied files before clearing it through the shared state boundary. There is no separate dependency registry, installer receipt, task runner or Corepack requirement.
- `WorkspaceFiles.apply()` compares desired, previously applied and currently observed bytes/modes, rejects conflicts before mutation, and journals the whole before/after set. `inspect()` shares the file comparison and parent-collision rules without writes. `recover()` checks initialization progress without reading credentials, observes stopped file intent and cleans only verified temporary replacements before state reconciliation. Replacements use same-directory temporary files and rename; new files use exclusive creation. It removes only unchanged, previously owned files and never recursively removes application directories.
- `WorkspaceSources.use()` borrows a working tree or acquires a specified Git repository/ref in scoped storage. Borrowed dirty files and acquired committed source remain distinct; detached output outlives the source lease.
- `Composition.prepare()` captures selected inputs, resolves registry/package dependencies, prepares on disk, reads back detached bytes with their source/template/policy origins, and detects relevant source changes before publication. Attribution travels with the output; Explain does not maintain a second planner or inventory.
- Application baseline, hostname and template helpers remain inside that composition boundary. They are not additional services or command modes.
- `SourceInventory` discovers current Git-visible files, including untracked additions and excluding deletions. Its separate `localEnvironment()` query returns ignored environment paths from the primary worktree and current checkout, never their contents. It is not a second filesystem abstraction. Git queries check exit status rather than treating failed discovery as an empty inventory.
- `Shadcn` delegates loading/hydration to upstream. Installation runs in a private one-shot worker, with parent-owned completion checks and redacted diagnostics.
- Staging uses `acquireUseRelease` and operation-local state. Interrupted I/O is joined; unconfirmed worker completion retains storage. A successful worker message alone does not authorize deletion or publication.

## Operating limits

Creation/acquisition, native Add, local initialization/refresh, Explain, Check, snapshots, Diff, bounded recovery, authorized lock breaking and Watch share this implementation. Applied ownership and snapshot attribution are persisted separately from current-source explanation. Local initialization and named refresh install dependencies by default; explicit `--no-install` reports dependencies pending and never advances successful-install evidence. Named workspaces may already contain settings, environment files, caches and arbitrary local files. Initialization and refresh leave unowned files untouched unless they collide with intended output, in which case publication stops before changing application files. Diff reports eligible unowned paths without adopting or snapshotting them. Absent or invalid receipts never authorize adoption. Fresh project creation still requires an empty destination. Preserve local edits and private state before reinitialization; a receipt is not a backup.

The `test-reference-workspace`, `reference-workspace-bindings` and `lint-workspaces` modules cover maintainer verification. Application tasks use ordinary Turbo from the composed workspace; Compose does not run them. Browser tests run through that workspace's own scripts after explicit composition and never refresh an already running app. Lint uses scoped copies, identifies production templates through the source registry and reports errors against their canonical origins.

Vercel settings install the root tooling dependency closure and compose the named application during installation. The Build Command invokes Turbo from the installed application workspace root, with no source-level affected gate or generated task inventory. Install and build remain inside Vercel's Git deployment; Root Directory remains the selected app.

Installation readiness is bounded evidence, not proof of every `node_modules` byte or application startup. Named synchronization compares desired installation inputs and Node/pnpm execution identity, checks the observed root/virtual lockfiles and pnpm layout marker, and verifies required direct dependency manifests still exist. The standard isolated pnpm layout is the implemented output contract; alternative layouts need separate coverage. Optional dependencies may be absent. pnpm-normalized lockfiles retain distinct desired and applied fingerprints: component-only refresh preserves normalization, while a new canonical lockfile replaces it and requires reconciliation.

Lifecycle hooks, local/injected dependencies, pnpm hooks or installation-affecting environment configuration disable reuse. An `.npmrc` containing only comments and literal authentication assignments does not invalidate an already installed graph. Inspection classifies assignment keys without retaining or fingerprinting credential values; other settings and unrecognized syntax require reconciliation. Configuration environment values are not read or fingerprinted. This is not a complete cache key for arbitrary external/global configuration. pnpm runs with inherited environment and terminal stdout/stderr; third-party lifecycle output is not guaranteed secret-free, but it is not stored in receipts or our typed errors. The command remains `pnpm install`, optionally `--offline`, with `--no-frozen-lockfile`.

Launch and nonzero-exit failures allow an explicit retry only when the installed input graph remains unchanged. Changed manifests, ambiguous lockfile changes and failed state publication retain incomplete evidence. Interruption remains Effect interruption; confirmed process stop must be recorded before the lease can be released. Neither outcome rolls back application files, removes dependencies or automatically reruns lifecycle scripts. The shared POSIX completion helper is exercised with a real process and descendant, including denied termination and another invocation recovering after a confirmed stop. Diff may inspect a stopped incomplete operation without recovery; Check rejects pending intent, and Sync reconciles only the bounded cases described above.

Named synchronization takes an exclusive directory lock before reading ownership or preparing source, retaining it through recovery, writes, explicit environment copying, verification, installation and snapshot publication. This deliberately serializes cooperating compositions for the whole operation; it does not lock editors or the canonical source checkout. Per-file writes finish before the lock can be released. An abandoned lock or corrupt receipt blocks state-based inspection and mutation; pending intent blocks Check but not an otherwise idle Diff. Sync attempts only verified file recovery or recovery of a recorded stopped installation. A failed receipt publication retains its temporary evidence and lock. Existing locks require the explicit recovery described above; no automatic stale-lock takeover or uncertain-process recovery is implemented. Ordinary refresh preserves settings, env files and caches; seeded ignore rules are not registered as managed application source.

The receipt stores fingerprints, not application contents. A pending intent includes unchanged files and any initial-only settings/env target paths with their progress, but never secret values or env fingerprints. The completed receipt excludes environment files. State publication uses a sibling filesystem rename, not an in-place JSON rewrite; this is not a power-loss durability guarantee. Application publication is sequential, not a directory-wide transaction, and cannot eliminate races with an uncoordinated editor between observation and rename. File/directory shape transitions are rejected rather than resolved by recursive deletion.

Named initialization preserves authored settings and skips the registry's app ignore/deployment defaults. It seeds a root `.gitignore` only when missing; existing rules, including an empty file, remain unchanged. Deployment settings must belong to a selected application. Cache contents are left alone, and registry output cannot claim cache paths or workspace settings. Predictable output-path collisions fail before any application files are published. Fresh projects retain application ignore/deployment defaults and still require an empty destination; they do not inherit the named-workspace preservation policy.

Composition preserves `.env.example`, `.env.sample` and `.env.template` as documentation. It does not turn examples into runtime env files or seed variables; provisioning owns creating values. Registry files, templates and assets targeting runtime env files are rejected before publication. Existing env bytes and permissions are preserved. `compose <name> --no-install --copy-env` explicitly copies missing ignored local env files at the source root or beneath apps/packages/tests, excluding runtime caches. Current-checkout values take precedence over primary-worktree fallback. Only directories belonging to materialized output receive copies, with private permissions and no hostname rewriting. Discovery occurs only when requested, and secret bytes are read during env copying, outside preparation and managed-source reporting. The one synchronization result reports created env paths/counts, never values or fingerprints. Provisioning commands are separate from composition.

Environment preflight runs before application publication. Missing sources or occupied non-file env targets stop the operation. A later read/write failure returns `EnvironmentInitializationFailed`, identifies the target and completed env paths, and keeps its underlying diagnostic redacted. A partially created file is preserved for inspection, not overwritten or deleted. Named synchronization leaves its intent pending until this phase and file verification finish, so a later invocation cannot treat a partial credential copy as successful initialization. Recovery uses the per-target progress rules above, not a comparison of secret values.

Registry support includes local item names/selection IDs, repository-qualified references derived from the registry's GitHub homepage, official provider shorthand, the shared `app-web` entry, transitive registry dependencies, conditional package/recipe dependencies, selected package/recipe provider requirements, and exact `registry:file`/`registry:page` targets inside `registry:item`. Every provider named in a condition must be selected; newly reached recipes participate in the same closure, and dependency cycles do not duplicate output. Inactive dependencies are not acquired and inactive recipe bodies are not read; the source catalog still supplies structural validation and ownership metadata. Explicit add-on choices must identify add-ons, not providers, packages or recipes; plain ShadCN items can enter through registry dependencies. Required or forbidden provider mismatches fail before staging/publication. Compatibility declarations are checked against the complete selected graph before reading selected source files; failures report the declaring selection, missing requirements and conflicts. Presets resolve their selections and may be combined with additional add-ons, but not explicit provider overrides.

Module-reference templates support `wrapper`, `element`, `call`, `factory`, `members`, and `graphql`, plus conditional sections. Binding order is explicit priority, registry owner, then export; closing wrappers reverse that order. GraphQL spreads retain fragment names while document references use local import aliases. Invalid or ambiguous templates fail before publication. Template targets are registry-owned even inside otherwise copied packages, so precomposed source files cannot reintroduce unselected features.

Provider dependencies bind stable aliases to the selected implementation. Registry-owned package entries are reconciled before following internal dependencies, including entries in root manifests and transitively discovered packages. The same reconciled manifests are written to output; unselected provider packages cannot enter through baseline fallback. Conflicting requirements and missing consumers fail before publication. Provider `sourcePath` bindings and explicit registry `typeScriptAliases` update TypeScript paths relative to the materialized application, preserving unrelated JSONC settings and comments. Unselected owned aliases are removed, and competing mappings fail before publication; no maintainer-only resolver path is introduced.

ShadCN `dependencies` and `devDependencies` from the selected registry graph populate the application root manifest. Package-local declarations continue to use `meta.nextHydra.packages`. Named specifiers, including scoped packages and npm aliases, are preserved; a bare name retains an existing declaration or defaults to `latest`. Among selected registry requests, runtime dependencies take precedence over development-only requests. Different explicit specifiers for the same root dependency, including conflicts with root-targeted package declarations, fail before publication; composition does not attempt semver negotiation. Unnamed URLs and paths are rejected because they do not identify a manifest key without acquisition. Root `workspace:` requirements participate in internal package closure. Refresh reconstructs the manifest from current selections, removing deselected requirements while retaining application tooling. Preparation strips npm declarations from the upstream installation request; dependency installation belongs to Sync, not the ShadCN preparation worker.

Registry assets are captured and copied byte-for-byte, including text assets whose contents resemble application URLs. They do not pass through hostname rewriting. Selected pnpm patch declarations must reference a selected asset and cannot disagree about the patch for the same dependency. Selected declarations reach pnpm workspace settings, and matching lockfile entries remain resolution seeds; unselected patches and assets stay out of output. pnpm applies selected patches during installation; their declared contents participate in installation invalidation.

The application root receives application tooling/scripts rather than the maintainer's lifecycle hooks and tooling dependencies. Captured pnpm settings retain catalogs and install settings but discover only materialized app/package roots. The lockfile is a seed: unrelated importers are removed, existing resolution data remains, and the later installation step must reconcile changed manifests. It is not promised to pass a frozen install before reconciliation. Turbo receives the existing application task policy, not the maintainer task graph. Apps retain Portless development commands with stable `<app>.<workspace>` names; exact declared hostname references are rewritten without file-extension lists. These rules apply to fresh and named materialization alike.

Published registry acquisition, preset resolution, repository/ref creation, development port settings and metadata validation are implemented. Published artifacts cannot read source-only templates or binary assets from the local checkout; normal artifact files and bindings remain supported. ShadCN `envVars` transformations are outside fresh/named composition, where runtime env output is rejected; explicit native Add delegates them as described above. All four maintained workspaces have been initialized and installed through the active executable and pass Check. Five standalone scaffold checks cover both CMS-only projects and the storefront provider selections, including a full Contentstack/WorkOS production build with synthetic configuration values. The authored packed example also passes build and runtime execution. These checks do not establish live CMS, auth, commerce or hosted Vercel behavior.

Process completion is exercised on Linux. Windows worker installation is rejected before launch until its completion policy is implemented and tested. The POSIX process-group policy does not claim containment of arbitrary processes that deliberately escape their group.

No automatic rollback is promised after destination publication starts. A write failure reports the failed target and completed files, retains private diagnostics, and leaves those files available for inspection.
