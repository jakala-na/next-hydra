# Existing Cart behavior and provider leakage

Research snapshot: `0a9e45d404614977147bcc929d4aeb587ee75a77` (`checkout`). This note inventories the current implementation; it does not propose the replacement design.

## Current-state flow

```text
Storefront layout / CartProvider
  locale -> StoreContext -> context-matched anonymous Cart cookie
  -> cartService.getCartById -> cartRepo GraphQL -> Cart + Cart Policy issues

Storefront Cart mutations
  StoreContext -> same anonymous Cart lookup
  -> create if add has no readable Cart / update by Cart id + numeric version
  -> cartRepo GraphQL -> updated Cart -> Cart Policy issues -> CartProvider state

Web Checkout
  WorkOS session
    -> authenticated: auth user -> Customer -> Store-scoped Business Unit context
    -> anonymous: context-matched Cart cookie
  -> CommerceRequestContext -> CheckoutScope -> CheckoutSession
  -> cartService/cartRepo -> Checkout State

Checkout HTTP
  locale + bearer JWT and/or anonymous cookie/header
  -> authenticated scope takes precedence, otherwise anonymous possession
  -> CheckoutSession -> recomputed Checkout API State
```

The old Cart seam is not one boundary. Storefront callers use global Promise-based `cartService`/`cartRepo` values directly, while `layerCommercetoolsCheckoutSession` is an Effect `Layer` whose implementation still closes over that same global `cartService`. Runtime Layer composition can replace Checkout policies, Store contexts, Commerce accounts, and Address Book implementations, but not Cart persistence. (`packages/commerce/lib/cart/cart.service.ts:17-90`; `packages/commerce/lib/checkout/commercetools.ts:391-440`; `packages/commerce/lib/checkout/commercetools.test.ts:11-29`)

## Selection, authorization, and caller inventory

### Storefront layout read

- `apps/web/app/[locale]/layout.tsx` resolves `StoreContext` from locale, starts `getCartForContext`, and gives its promise plus the three server actions to `CartProvider`. (`apps/web/app/[locale]/layout.tsx:29-32`, `apps/web/app/[locale]/layout.tsx:61-73`)
- `getCartForContext` is explicitly anonymous-only. It reads a Cart id from the `cart` cookie, returns `NOT_FOUND` if absent, fetches that id, evaluates Cart Policies, and returns `{ cart, issues, currency }`; authenticated Cart support is a TODO. (`packages/commerce/lib/cart/utils/get-cart.ts:14-38`)
- The cookie contains Cart id, currency, locale, and Store key. It is accepted only when all three context fields match; it is HTTP-only, SameSite=Lax, production-secure, path-wide, and retained for 90 days. (`packages/commerce/lib/cart/utils/anonymous-cart-cookies.ts:11-28`, `packages/commerce/lib/cart/utils/anonymous-cart-cookies.ts:78-107`, `packages/commerce/lib/cart/utils/anonymous-cart-cookies.ts:113-135`; tests: `packages/commerce/lib/cart/utils/anonymous-cart-cookies.test.ts:17-75`)
- After the context match, the provider read is `cart(id: $id)` only. It does not also constrain or validate the returned Cart's Store, anonymous id, state, or customer ownership. Thus the current anonymous authorization fact is possession of the context-matched Cart-id cookie, not a provider-side ownership predicate in this read. (`packages/commerce/lib/cart/cart.repo.ts:335-344`, `packages/commerce/lib/cart/cart.repo.ts:648-669`)
- `CartProvider` carries the complete `CartWithIssues`, but its current hooks derive only line-item id/name/image/unit price/quantity, total item count, calculated display total, and currency; no hook surfaces `issues`. Action success replaces the shared Cart and errors become generic toasts. (`packages/design-system/components/commerce/providers/cart-context.tsx:34-49`, `packages/design-system/components/commerce/providers/cart-context.tsx:90-112`, `packages/design-system/components/commerce/providers/cart-context.tsx:137-243`)

### Add item and anonymous Cart creation

- The action receives only product id, string variant id, and quantity. `inStoreAction` adds the locale-derived `StoreContext`, including currency, Store id/key, and distribution channel. (`packages/commerce/contracts/actions/add-to-cart.ts:6-14`; `packages/commerce/lib/utils/safe-action.ts:34-44`; `packages/commerce/lib/store/types.ts:29-37`)
- It first runs the anonymous current-Cart read. Any non-success result—not only `NOT_FOUND`—is treated as no Cart and causes creation. Creation uses Store currency and Store id; the new id is persisted in the anonymous cookie. (`packages/commerce/actions/add-to-cart.ts:23-47`; `packages/commerce/lib/cart/cart.service.ts:32-42`; `packages/commerce/lib/cart/cart.repo.ts:671-698`)
- The item write passes Cart id and numeric version from the fetched/created Cart, parses variant id to a number, and adds a Commercetools line item with the Store's first distribution-channel key. Missing channel is a thrown error. (`packages/commerce/actions/add-to-cart.ts:49-58`; `packages/commerce/lib/cart/cart.service.ts:45-55`; `packages/commerce/lib/cart/cart.repo.ts:346-368`)
- On success the action re-evaluates policies and returns the full updated Cart, Store currency, and violations. Creation/add failures are collapsed to generic `UNKNOWN` action errors. (`packages/commerce/actions/add-to-cart.ts:44-76`)

### Quantity change and item removal

- Both actions accept buyer intent only (`lineItemId`, plus quantity for change), but first read the anonymous current Cart and then pass its id and numeric version directly to exported `cartRepo` functions, bypassing `cartService`. (`packages/commerce/contracts/actions/change-cart-items-quantity.ts:6-15`; `packages/commerce/contracts/actions/remove-cart-item.ts:6-12`; `packages/commerce/actions/change-cart-items-quantity.ts:21-35`; `packages/commerce/actions/remove-cart-item.ts:21-34`)
- Provider mutations use `changeLineItemQuantity` and `removeLineItem` update actions. Each retries once with the provider-reported current version, then returns the updated Cart. Caller-visible write failures are collapsed to generic `UNKNOWN`; successful writes re-evaluate policies and preserve the same `CartWithIssues` response shape. (`packages/commerce/lib/cart/cart.repo.ts:370-410`, `packages/commerce/lib/cart/cart.repo.ts:740-819`; test: `packages/commerce/lib/cart/cart.repo.test.ts:506-546`; actions: `packages/commerce/actions/change-cart-items-quantity.ts:37-53`, `packages/commerce/actions/remove-cart-item.ts:36-52`)

### Checkout scope and current read

- Web Checkout gives authenticated sessions precedence. It validates the WorkOS user id, resolves `CustomerId`, then resolves exactly one Business Unit context for that Customer in the locale-derived Store. The resulting principal carries auth user id, Customer id, Business Unit id/key, and locale. Anonymous web Checkout instead requires the context-matched Cart cookie. (`apps/web/lib/checkout-scope.ts:35-90`, `apps/web/lib/checkout-scope.ts:93-120`, `apps/web/lib/checkout-scope.ts:122-153`)
- Checkout HTTP prefers a valid bearer principal over anonymous possession. Without a bearer it prefers the context-matching cookie over `x-context-anonymous-cart-id`; an invalid bearer does not fall back to anonymous. (`apps/api/lib/checkout/http.ts:117-140`, `apps/api/lib/checkout/http.ts:354-435`; tests: `apps/api/__tests__/checkout-rest-route.test.ts:1377-1535`)
- Anonymous Checkout selects by the possessed Cart id. Customer Checkout queries through Commercetools `asAssociate(associateId, businessUnitKey)` and filters for `cartState="Active"` plus the locale-derived Store key. Zero results are unavailable; more than one is an explicit conflict rather than an arbitrary choice. (`packages/commerce/lib/checkout/commercetools.ts:67-113`; `packages/commerce/lib/cart/cart.repo.ts:312-333`, `packages/commerce/lib/cart/cart.repo.ts:591-646`; tests: `packages/commerce/lib/cart/cart.repo.test.ts:175-205`, `packages/commerce/lib/cart/cart.repo.test.ts:257-321`)
- The customer scope includes Business Unit id, but Cart selection authorizes through Customer/associate id, Business Unit key, and Store key; Business Unit id is subsequently read from the Cart to construct the Checkout buying context. (`packages/commerce/domain/checkout.ts:25-49`; `packages/commerce/lib/checkout/commercetools.ts:157-179`)
- Provider `Cart` is decoded into `CartForCheckout`: id, numeric version, optional Customer/Business Unit/anonymous/Store identity, line-item ids/product ids/names/quantity/total/variant id/SKU, total quantity, and total price. Provider-only `cartState` is dropped. (`packages/commerce/domain/cart.ts:35-60`; `packages/commerce/lib/cart/cart-for-checkout.ts:19-90`; test: `packages/commerce/lib/cart/cart-for-checkout.test.ts:31-70`)
- `getCurrent` also derives persisted Checkout details, B2B/guest buyer context, Cart Policy violations, Checkout Policy violations, ordered steps, active step, and rejects missing or empty Carts. (`packages/commerce/lib/checkout/commercetools.ts:181-201`, `packages/commerce/lib/checkout/commercetools.ts:399-425`; `packages/commerce/lib/checkout/state.ts:156-208`)

### Checkout Contact mutation

- Both server-action form and HTTP payload publicly require `{ cart: { id, version } }`; the rendered form exposes both as hidden values. (`packages/commerce/domain/checkout.ts:100-104`; `packages/commerce/actions/save-checkout-contact.ts:15-33`, `packages/commerce/components/pages/checkout-contact-form.tsx:15-45`; `packages/commerce/http/checkout-api.ts:97-102`)
- Live orchestration resolves the authoritative current Cart from trusted scope and compares only submitted Cart id. The submitted numeric version is not used for the write; the freshly fetched provider Cart's version is used. A different submitted id becomes `CheckoutCartMismatch`. (`packages/commerce/lib/checkout/checkout-session.ts:442-458`; `packages/commerce/lib/checkout/commercetools.ts:226-246`)
- Repeating an already-persisted contact is a no-op. Otherwise persistence writes `customerEmail` and JSON contact data in Custom Type `orderCustomFields`, field `checkoutContact`. It rejects a different existing Custom Type. (`packages/commerce/lib/cart/checkout-contact-actions.ts:6-8`, `packages/commerce/lib/cart/checkout-contact-actions.ts:39-105`; `packages/commerce/lib/checkout/commercetools.ts:233-237`)
- Anonymous writes use GraphQL action shapes. Customer writes use the Commercetools REST associate/Business Unit Cart endpoint and SDK `CartUpdateAction` shapes. (`packages/commerce/lib/cart/cart.repo.ts:412-424`, `packages/commerce/lib/cart/cart.repo.ts:440-467`, `packages/commerce/lib/cart/cart.repo.ts:821-916`; test: `packages/commerce/lib/cart/cart.repo.test.ts:325-374`)
- `setCustomType` is not replayed merely by substituting a new version. On conflict, Checkout orchestration reloads the current Cart, re-checks identity, rebuilds the action according to the now-current Custom Type, and retries once. If the type already existed, the narrow `setCustomField` path can reuse the provider version. (`packages/commerce/lib/checkout/commercetools.ts:239-305`; test: `packages/commerce/lib/checkout/commercetools.test.ts:82-143`; lower-level preservation: `packages/commerce/lib/cart/cart.repo.ts:478-489`, `packages/commerce/lib/cart/cart.repo.test.ts:595-626`)

### Checkout Delivery Details mutation

- The form/HTTP contract also carries Cart id/version plus either manual address intent or an Address Book reference. The current Cart is resolved from trusted request context and only submitted id is checked. (`packages/commerce/actions/save-checkout-delivery-details.ts:44-48`, `packages/commerce/actions/save-checkout-delivery-details.ts:103-121`; `packages/commerce/http/checkout-api.ts:104-109`)
- Manual input is normalized and structurally validated. Customer-only Address Book intents resolve/save against the verified customer principal. An identical persisted Shipping Address is a no-op; otherwise the Cart stores the canonical address snapshot and, for Address Book sources, an encoded reference in the provider address `key`. (`packages/commerce/lib/checkout/checkout-session.ts:237-289`, `packages/commerce/lib/checkout/checkout-session.ts:356-413`; `packages/commerce/lib/checkout/commercetools.ts:315-365`; `packages/commerce/lib/cart/checkout-delivery-details-actions.ts:20-68`)
- Anonymous delivery uses GraphQL; customer delivery uses the associate/Business Unit REST path. The single narrow `setShippingAddress` action retries once with the provider-reported version. Exhausted conflicts remain typed Checkout version conflicts. (`packages/commerce/lib/cart/cart.repo.ts:919-997`; tests: `packages/commerce/lib/cart/cart.repo.test.ts:415-476`, `packages/commerce/lib/cart/cart.repo.test.ts:548-593`, `packages/commerce/lib/cart/cart.repo.test.ts:628-673`)
- When saving a new Address Book entry succeeds but Cart persistence or the response read fails, the stable Address Book reference is returned in the error so the caller can retry only the Cart phase. The HTTP handlers recompute and return current Checkout State after successful Contact or Delivery mutations. (`packages/commerce/lib/checkout/checkout-session.ts:415-439`; `packages/commerce/lib/checkout/commercetools.ts:367-387`; `apps/api/lib/checkout/http.ts:546-645`)

## Provider leakage across the current seam

1. **Provider revision is public domain/application state.** Numeric `version` is mandatory on `Cart`, `CartForCheckout`, `CheckoutCartReference`, storefront mutation parameters, Checkout State/API payloads, and rendered hidden form fields even though live Checkout ignores the submitted value. (`packages/commerce/lib/types.ts:177-213`; `packages/commerce/domain/cart.ts:50-60`; `packages/commerce/lib/cart/types.ts:16-23`, `packages/commerce/lib/cart/types.ts:47-72`; `packages/commerce/domain/checkout.ts:100-104`, `packages/commerce/domain/checkout.ts:235-243`; `packages/commerce/components/pages/checkout.tsx:160-187`)
2. **Provider Cart shape crosses every layer.** The shared `Cart` includes Commercetools-like `custom.type.key`, `customFieldsRaw`, nullable `store.key`, `cartState`, `origin`, and version. It is returned to storefront UI/policies and retained alongside the Checkout projection as `providerCart`. (`packages/commerce/lib/types.ts:177-213`; `packages/commerce/lib/checkout/commercetools.ts:127-155`; `packages/commerce/lib/cart/policy/cart-policy.types.ts:1-18`)
3. **Custom Type mechanics sit above provider infrastructure.** Cart helpers name `orderCustomFields`/`checkoutContact`, inspect the provider Custom Type, double-encode the GraphQL custom-field value, build GraphQL-shaped actions, and translate domain addresses to Commercetools address names/keys. Checkout orchestration itself imports the Custom Type key to choose retry strategy. (`packages/commerce/lib/cart/checkout-contact-actions.ts:6-40`, `packages/commerce/lib/cart/checkout-contact-actions.ts:59-105`; `packages/commerce/lib/cart/checkout-delivery-details-actions.ts:1-18`, `packages/commerce/lib/cart/checkout-delivery-details-actions.ts:39-68`; `packages/commerce/lib/checkout/commercetools.ts:16-27`, `packages/commerce/lib/checkout/commercetools.ts:263-284`)
4. **Update and transport mechanics are concentrated but not fully hidden.** `cart.repo.ts` owns Commercetools GraphQL documents, REST `asAssociate` calls, SDK `CartUpdateAction`, mapping, and error inspection; however callers still supply provider Cart/version and Checkout scope. (`packages/commerce/lib/cart/cart.repo.ts:1-50`, `packages/commerce/lib/cart/cart.repo.ts:160-230`, `packages/commerce/lib/cart/cart.repo.ts:294-438`, `packages/commerce/lib/cart/cart.repo.ts:440-507`)
5. **Commercetools conflict types and recovery leak into Checkout orchestration.** `CheckoutSession`'s Commercetools Layer imports and runs `retryVersionedWrite`, interprets `currentVersion`, mutates provider Cart versions, and maps generic `DomainError` values into Checkout failures. (`packages/commerce/lib/checkout/commercetools.ts:24-31`, `packages/commerce/lib/checkout/commercetools.ts:203-305`; provider decoder/retry: `packages/commerce/lib/infra/commercetools/versioned-write.ts:3-49`, `packages/commerce/lib/infra/commercetools/versioned-write.ts:90-139`, `packages/commerce/lib/infra/commercetools/versioned-write.ts:190-240`)
6. **Failure typing is lossy and can retain raw provider causes.** The seam returns `ActionResult` with broad string codes and optional raw `cause`; storefront mutations collapse failures to `UNKNOWN`, while Checkout re-wraps them into typed failures. (`packages/commerce/lib/utils/errors.ts:1-34`; `packages/commerce/lib/cart/cart.repo.ts:469-485`; `packages/commerce/actions/add-to-cart.ts:44-61`; `packages/commerce/lib/checkout/commercetools.ts:53-65`, `packages/commerce/lib/checkout/commercetools.ts:292-305`)
7. **Composition is static.** `cartService`, `cartRepo`, GraphQL client, API root, Store service, and Cart Policy registry are module singletons. Tests replace Cart through module mocking, not a Cart Service test Layer. (`packages/commerce/lib/cart/cart.service.ts:6-15`, `packages/commerce/lib/cart/cart.service.ts:82-90`; `packages/commerce/lib/cart/cart.repo.ts:15-16`, `packages/commerce/lib/cart/cart.repo.ts:52-52`, `packages/commerce/lib/cart/cart.repo.ts:1000-1009`; `packages/commerce/lib/cart/policy/cart-policy.service.ts:123-124`; `packages/commerce/lib/checkout/commercetools.test.ts:17-29`)

## Observable compatibility contract

- Preserve the storefront's current anonymous Cart promise/action contract: missing Cart reads as no Cart, add creates and cookies a Store/currency/locale-scoped Cart, mutations return updated Cart plus currency and non-blocking policy violations, and the client replaces local state from successful action results. There are currently no focused tests for the three storefront Cart server actions; source is the only direct evidence for their error-collapse and create-on-any-read-failure behavior.
- Preserve the current scope split unless separately changed: storefront Cart UI is anonymous-cookie-only; Checkout supports anonymous possession and authenticated Store + Business Unit associate selection. Anonymous and authenticated B2B Carts are not merged.
- Preserve authenticated precedence and anti-spoofing: verified auth resolves Customer/Business Unit scope, arbitrary customer headers are ignored, and invalid bearer credentials do not fall back to anonymous possession. (`apps/api/__tests__/checkout-rest-route.test.ts:1452-1535`)
- Preserve exact customer Cart selection semantics: active Cart, scoped to Store and Business Unit associate access, zero means unavailable, multiple means conflict, and provider authorization failures must not be misreported as missing. (`packages/commerce/lib/cart/cart.repo.test.ts:175-205`, `packages/commerce/lib/cart/cart.repo.test.ts:257-321`)
- Preserve Checkout's schema-backed Cart projection, non-empty requirement, details/step derivation, Cart and Checkout Policy evaluation, localized violation output, and recomputed state after mutation. (`packages/commerce/lib/cart/cart-for-checkout.test.ts:31-70`; `packages/commerce/lib/checkout/state.ts:156-208`; `apps/api/lib/checkout/http.ts:514-645`)
- Preserve mutation identity and idempotency behavior: scope selects the authoritative Cart; submitted Cart id detects stale/wrong UI; repeated Contact or Delivery values do not write; provider version conflict handling is bounded and mutation-aware; Cart mismatch and exhausted conflict remain stable conflict outcomes. Submitted version is currently wire-visible but not authoritative.
- Preserve Contact persistence as customer email plus `checkoutContact`, Custom Type conflict behavior, Delivery persistence as a Shipping Address snapshot, Address Book identity via address key, and partial-failure Address Book references.
- Preserve public failure shielding: Checkout exposes stable 400/404/409/500 codes and localized messages rather than raw provider details; storefront currently exposes only the broad `ActionResult` contract and generic UI failure messages. (`packages/commerce/http/checkout-api.ts:33-88`; `packages/commerce/actions/save-checkout-contact-state.test.ts:41-82`; `packages/commerce/actions/save-checkout-delivery-details-state.test.ts:44-101`)
