Registration Architecture Map

The current hierarchy from app-facing adapters through Effect use-case programs, provider-independent capability services, provider adapters, and storage.

Transport / app seam Use-case program Registration module Capability module Provider adapter Storage
App-facing seams

apps/web UI + Server Actions

Owns user interaction, form shape, view models, and cache revalidation.

apps/api HTTP adapter

Owns HTTP schemas, auth/header extraction, response status mapping.

Workflow adapter

Starts and resumes workflow runs that must execute in the API app.

Local callers

Jobs, tests, admin code, or server code that can use local Effect layers.

Use-case programs

submitRegistrationForReview

Public Registration intake: accepts company details, checks eligibility, and creates an awaiting approval Registration.

checkRegistrationEligibility

Preflight policy for pending email, Commerce customer, identity user, country, and VAT checks.

acceptRegistrationReviewDecision

Reviewer decision acceptance: marks approval processing and resumes workflow through an injected edge function.

RegistrationOnboarding

Workflow-called programs: provision Commerce, issue invitations, finalize approved or rejected state.

RegistrationNotifications

Existing workflow-called module: read current state and send the right Registration email.

CompanyMemberInvitations

Existing-company invitation use cases over invitation, policy, and Commerce capabilities.

Registration core

Registrations

Owns the Registration aggregate persistence and lifecycle: create awaiting approval, get, mark processing, mark approved, mark rejected. It should not own provider preflight checks.

Capabilities

RegistrationQueries

Read-model capability for list, cursor, search, and pending Registration email lookup.

VersionedKeyValueStore

Schema-aware optimistic-concurrency storage capability.

CommerceAccounts

Provider-independent Commerce account and customer checks.

IdentityUsers

Provider-independent identity lookup by normalized email.

Invitations

Issue, read, accept, and revoke provider invitations.

RegistrationMarketPolicy

Answers whether a company country can register.

VatValidator

Answers whether a submitted VAT identifier is acceptable.

RegistrationEmails

Registration-specific email sending capability.

Implements CommerceAccounts.

Ownership Notes

The main rule: capability services are replaceable seams supplied by Layer; use-case programs compose those capabilities; adapters expose programs over HTTP, workflow, server actions, jobs, or tests.

HTTP adapter

Thin transport seam. It should translate HTTP into module calls and map module errors back to HTTP responses.

Programs Effect.fn

Own Registration use-case ordering and policy. They are exported functions, not new capability services by default.

Registration intake

`submitRegistrationForReview` uses `checkRegistrationEligibility`, then creates an awaiting approval Registration.

Registration review

`acceptRegistrationReviewDecision` marks processing before resuming workflow, and does not resume after transition conflicts.

Registrations

Owns versioned aggregate storage and lifecycle transitions only. This keeps ADR-0001 intact.

RegistrationQueries

Owns read-model behaviour that key-value Registration storage should not promise, including search and pending email lookup.

Workflow adapter

Remains API-owned. HTTP passes a small resume function into the review program when asynchronous processing is required.
