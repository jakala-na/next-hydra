# Current Address Book and Checkout seams

## Finding

The repository already has reusable seams for verified Buying Context, associate-scoped Cart access, resolved Shipping Address persistence, typed Checkout failures, and localized adapters. It has no Address Book model or capability. The smallest compatible addition is a separate Business Unit Address Book service plus a submitted Delivery Details input union; the resolved `CheckoutDeliveryDetails` stored on the Cart and exposed in Checkout State can remain unchanged.

## Current-state flow

1. **Resolve trusted Buying Context.** The web adapter derives the authenticated user from WorkOS, maps it to a Commercetools Customer, resolves exactly one associated Business Unit inside the locale's Store, and puts Customer and Business Unit IDs/keys into `StorefrontCustomerCheckoutScope` (`apps/web/lib/checkout-scope.ts:38-95`). The public HTTP adapter performs the equivalent flow from a verified bearer JWT and deliberately derives the Customer and Business Unit rather than trusting a submitted identity (`apps/api/lib/checkout/http.ts:270-324`). `CustomerCommercePrincipal` and the resulting customer Checkout Scope already carry both Business Unit ID and key (`packages/commerce/domain/commerce-request-context.ts:22-30`, `packages/commerce/domain/checkout.ts:33-42`).

2. **Enforce Store and associate scope at Commercetools.** `CommerceAccounts` resolves Buying Context through a provider-independent Effect service method (`packages/commerce/services/commerce-accounts.ts:138-175`). Its Commercetools Layer queries Business Units inside the Store using direct or inherited associate membership and fails closed when zero or multiple units match (`packages/commerce/lib/infra/commercetools/commerce-accounts.ts:314-374`). B2B Cart reads use GraphQL `asAssociate(businessUnitKey, associateId)` and a Store predicate (`packages/commerce/lib/cart/cart.repo.ts:268-289`, `packages/commerce/lib/cart/cart.repo.ts:464-500`); Cart writes use the REST associate/Business Unit path (`packages/commerce/lib/cart/cart.repo.ts:416-448`).

3. **Seed Business Unit addresses at registration.** Registration creates the initial address on the Business Unit, marks index `0` as both shipping and billing, and makes it the default; the Customer draft has no address fields (`packages/commerce/lib/infra/commercetools/commerce-accounts.ts:390-445`). There is currently no domain Address Book entry/reference type and `CommerceAccounts` exposes identity, profile, association, and Buying Context operations only (`packages/commerce/domain/commerce-account.ts:3-23`, `packages/commerce/services/commerce-accounts.ts:138-175`).

4. **Accept only Manual Delivery Details.** `ShippingAddress` is schema-backed and uses Address Line 1/2 plus a whitelisted Country Code. `CheckoutDeliveryDetails` always contains both a source and an already resolved Shipping Address, even though the source literal already includes `addressBook` (`packages/commerce/domain/checkout.ts:110-141`). The Server Action decodes manual form fields, constructs `source: "manual"`, calls `CheckoutSession.saveDeliveryDetails`, and converts the Effect result to action state (`packages/commerce/actions/save-checkout-delivery-details.ts:14-96`). `CheckoutSession` trims and validates manual fields and rejects any non-manual source (`packages/commerce/lib/checkout/checkout-session.ts:227-278`).

5. **Persist the resolved address and recompute Checkout.** The Commercetools Checkout Layer loads the scoped Cart, verifies its submitted ID/version, skips an equal persisted address, and delegates persistence to the Cart service (`packages/commerce/lib/checkout/commercetools.ts:254-313`). The Cart adapter maps Address Line 1/2 to Commercetools `streetName`/`additionalStreetInfo`, then uses associate-scoped persistence for B2B (`packages/commerce/lib/cart/checkout-delivery-details-actions.ts:37-59`, `packages/commerce/lib/cart/cart.repo.ts:736-760`). Checkout completion depends only on required fields of the resolved Shipping Address (`packages/commerce/lib/checkout/state.ts:62-87`), and `CheckoutState` contains Cart, details, steps, and violations—not option catalogs (`packages/commerce/domain/checkout.ts:204-212`).

6. **Keep adapters thin.** The HTTP schema currently accepts the resolved `CheckoutDeliveryDetails`; its handler resolves trusted scope, calls the same `CheckoutSession` mutation, maps typed failures, and returns recomputed state (`packages/commerce/http/checkout-api.ts:82-87`, `apps/api/lib/checkout/http.ts:445-487`). The Next.js action resolves scope, invokes the package action, and revalidates on success/conflict (`apps/web/app/[locale]/checkout/actions.ts:55-81`). The Checkout page currently fetches only Checkout State/translations and renders one manual address form whose errors are localized from stable action codes (`packages/commerce/components/pages/checkout.tsx:218-264`, `packages/commerce/components/pages/checkout-delivery-details-form.tsx:23-40`, `packages/commerce/components/pages/checkout-action-error.ts:8-22`).

## Smallest compatible extension points

- **Add a separate Address Book domain and Effect capability, not methods on Checkout State.** It should accept the already verified customer Checkout Scope/Buying Context and expose list, resolve, and idempotent add operations. Keep provider address shapes and Commercetools failures in its Layer; map them to schema-backed Address Book values and typed capability errors. `CommerceAccounts` should remain responsible for identity and Buying Context resolution.
- **Separate submitted intent from persisted details.** Introduce a Checkout action input union for: manual Cart-only address, existing Address Book Reference, and new address with explicit save intent. Keep `CheckoutDeliveryDetails` as the resolved Cart-owned result. This is the smallest way to satisfy reference submission without putting a copied address into the address-book request or preserving a reference in Checkout State.
- **Resolve before the existing Cart write.** Extend the `CheckoutSession.saveDeliveryDetails` use-case orchestration to call the Address Book capability for customer scope, producing the same normalized `CheckoutDeliveryDetails` consumed by the existing equality check and Cart persistence path. Compose the Commercetools Address Book Layer beside the current Checkout/Accounts Layers (`packages/commerce/lib/checkout/commercetools.ts:315-362`).
- **Load choices beside, not inside, Checkout State.** On authenticated Checkout, fetch Address Book entries independently and pass them to the Delivery Details form; anonymous Checkout retains Manual only. Extend the form schema/action state/error-code translation for selection, explicit save, stale/inaccessible reference, and add failure. Revalidation can continue to refresh Checkout State after the Cart save; retry state must retain the idempotency intent/reference when the address was created but the Cart update failed.
- **Extend the public adapter at the same action boundary.** Change `SaveCheckoutDeliveryDetailsRequest` to the submitted input union and extend typed error-to-HTTP mapping. Keep bearer-derived scope authoritative; no customer or Business Unit identity belongs in the payload.

## Issue 06 delta

Issue 06 already specifies reference-based submission, external resolution, trusted request context, Cart persistence of the resolved address, lean Checkout State, typed stale/missing/inaccessible failures, HTTP support, spoofing protection, and core save tests (`.scratch/checkout-effect-slice/issues/06-address-book-delivery-details-source.md:10-35`). The new plan must additionally specify the Address Book's list/add capability, Business Unit ownership, selectable shipping catalog, explicit Cart-only versus save-and-use intent, sequential Business Unit-then-Cart writes, retry idempotency after a partial failure, independent UI loading, and localized adapter/action codes.
