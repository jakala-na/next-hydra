# Scaffold-time stack provisioning

Type: grilling
Status: resolved
Blocked by: 05

## Question

How should `create-next-hydra` consume the contribution contract to provision a selected CMS provider, Commerce provider, their required bundles, and compatible optional add-ons into a new project?

Treat copied source as customer-owned immediately after materialization. Decide whether generated projects retain any non-destructive composition machinery or receive only materialized workspace units and aliased dependencies; define package-manager rewriting, additive file generation, diff/conflict behavior, environment and documentation output, installation timing, external Backend App or provider-native setup boundaries, failure reporting, and the distinction between deterministic workspace generation and external provisioning side effects. Do not assume the CLI may later remove or overwrite copied files.

## Comments

- Agreed staging location: the requested target directory is itself the scaffold staging area because `create-next-hydra` accepts only a missing or empty target and therefore may perform the requested initial writes there. V1 does not add a hidden sibling staging directory. Materialized files are user-owned even if a later scaffold step fails; the staging label does not authorize cleanup or later destructive management.
- Agreed scaffold failure behavior: the CLI never cleans a failed scaffold automatically, including after clone, registry materialization, package installation, Git initialization, or commit failures. It stops and reports the target path, exact failed step, completed work, and work not attempted, preserving the only concrete evidence of a bad Provider or partial installation. The user may inspect or repair it, compare it with another scaffold, retain it for a bug report, or delete it before retrying. The ordinary empty-directory check intentionally prevents an accidental retry over that evidence. A failed optional initial commit is a warning after successful composition, not a reason to discard the project.
- Agreed customer CLI boundary: a successful scaffold does not retain `create-next-hydra` as a dependency and does not ship registry or composition configuration for later management. Additive Installation is invoked on demand, for example with `pnpm dlx create-next-hydra add <item-or-registry-url>`; the caller may pin the CLI version when reproducibility matters.
- Agreed explicit-selection boundary: interactive scaffolding asks for every required Provider Slot. Non-interactive `--yes` requires explicit Auth, CMS, and Commerce choices or an explicit `--preset` that supplies them; it never inherits the Maintainer Workspace's Reference Composition. Add-ons are included only when selected by the user or preset, or when required transitively.
- Agreed preset purpose: `--preset` is the public CLI input for a reusable set of Provider and Add-on selections. It is an explicit composition request rather than a preferred stack or automatic default.
- Preset support confirmed: [ShadCN support for portable Next Hydra Presets](../research/04-shadcn-portable-preset-support.md) verifies that a fileless `registry:item` with `registryDependencies` and arbitrary `meta.nextHydra` is valid and that ShadCN can fetch and install its dependency graph. ShadCN does not interpret or retain Next Hydra metadata in the resolved install tree, so `create-next-hydra` must fetch the individual definitions, validate slots, compatibility, aliases, package-specific requirements, and target conflicts, show the plan, and only then call the public `addRegistryItems()` API. Registry mappings and private authentication may be supplied in memory rather than written into the Customer Workspace.
- Agreed Preset execution boundary: `create-next-hydra --preset` and the Next Hydra `add` command are the supported paths because they perform the semantic preflight before materialization. Raw `shadcn add` remains an inspection or escape-hatch command and is not a supported way to apply a Next Hydra Preset; it would ignore Next Hydra metadata and validation.
- Agreed v1 dependency handling: a Provider or Add-on item that materializes a complete workspace package or application includes its own `package.json`. Standard ShadCN dependencies belong to the root invocation; a dependency that belongs to a specific workspace package uses the typed `meta.nextHydra.packages` entry instead. For example, a Drupal-specific DAM integration targets frontend files into `packages/cms-drupal`, targets its module into `apps/drupal`, and declares any Drupal-package dependency against `packages/cms-drupal`. After all registry files and aliases are present, initial scaffolding runs one root `pnpm install` to settle the complete workspace. V1 does not automate Composer changes.
- Agreed v1 environment boundary: Next Hydra does not reject, suppress, or reinterpret ShadCN `envVars`; when a registry item declares them, ShadCN applies its normal behavior. Next Hydra-authored items use `envVars` only for safe development defaults or placeholders, never as a mechanism for obtaining or provisioning real secrets. Providers and Add-ons communicate required secret values through their ordinary example files and setup documentation, and the user supplies those values through normal environment management.
- Agreed setup-instruction output: installation instructions are terminal output only. The CLI does not create a combined setup file, composition receipt, or other retained instruction artifact in the Customer Workspace. A Provider or Add-on that needs durable documentation can include an ordinary README as part of its customer-owned source.
- Agreed external-system boundary: composition materializes local source, workspace packages and applications, Provider-owned application files, package aliases, ShadCN-supported additions, and JavaScript dependencies. It does not enable Drupal modules, change Composer requirements, register or deploy Merchant Center extensions, create remote CMS models, obtain secrets, or otherwise provision external provider state. Provider-native and Backend App activation steps are reported as terminal instructions.

## Answer

`create-next-hydra` first obtains explicit Auth, CMS, and Commerce choices plus any selected Add-ons, either interactively, through flags, or through a portable Preset. It fetches every Selection Definition and registry item before writing, expands the complete Composition Plan, validates Provider Slot cardinality, compatibility, aliases, dependency requirements, and target paths, and shows the resolved plan. `--yes` still requires explicit selections or an explicit Preset; the Maintainer Workspace's Reference Composition is never an implicit customer default.

The requested missing or empty target directory is the only scaffold working area. The CLI clones the complete Maintainer Workspace there, removes maintainer-only material and all variable Provider and Add-on source to leave the Baseline, then asks ShadCN once from the workspace root to install the selected dependency graph at its explicit final targets. Provider-specific Next.js routes are ordinary files in that graph. The CLI writes the selected Provider Alias entries and runs dependency installation. Complete contributed packages and applications bring their own manifests; package-specific dependency entries are applied explicitly before a final root `pnpm install` settles the composed workspace.

The successful Customer Workspace contains only the Baseline, selected source and application files, selected aliases, and resulting dependency state. It retains no Workspace Selection, registry authoring source, composition receipt, or `create-next-hydra` dependency. A later `create-next-hydra add` is an on-demand Additive Installation: it validates the requested item, discloses its changes, creates missing files, skips identical files, requires explicit approval or `--overwrite` for changed targets, and never removes customer code. `--yes` skips confirmation prompts but does not authorize overwrites; combine `--yes --overwrite` for an intentional fully non-interactive installation.

ShadCN retains its ordinary behavior for safe environment placeholders and development defaults, but Next Hydra items do not use it to obtain or provision real secrets. Setup instructions are printed only in the terminal unless an installed contribution includes its own ordinary README. The CLI materializes local code and installs JavaScript dependencies but does not enable provider-native modules, change Composer requirements, deploy Backend Apps, configure remote services, or perform other external provisioning.

Any failure leaves the target directory exactly as it stands. The CLI reports the failed step, completed work, and unattempted work without rollback or cleanup so the user can inspect, repair, compare, report, or delete the partial scaffold. Git initialization and the optional initial commit happen last; commit failure is a warning rather than a reason to discard an otherwise composed project.
