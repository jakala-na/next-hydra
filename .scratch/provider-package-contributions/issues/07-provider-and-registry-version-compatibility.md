# Provider and registry version compatibility

Type: grilling
Status: resolved
Blocked by: 06

## Question

How should Next Hydra version Selection Definitions, Composition Plans, Provider Alias interfaces, and Registry Artifacts so a CLI can tell whether a Provider, Add-on, Preset, or existing workspace is compatible with it?

Decide what is versioned independently, how registry references are pinned or allowed to float, how compatibility ranges are declared, what happens when an item requires a newer CLI or alias interface, and what an on-demand Additive Installation may call an upgrade when the Customer Workspace has no authoritative composition receipt and owns all copied code. Preserve the established rule that customer changes are not overwritten or removed automatically.

## Comments

- Agreed Customer Workspace boundary: v1 has no project-upgrade operation. An on-demand `add` installs the specifically requested Registry Artifact through Additive Installation and reports current file and dependency conflicts, but it cannot determine or claim that a customer-modified workspace as a whole matches a known Next Hydra version. Complete governed recomposition applies only to the Maintainer Workspace and initial closed-world scaffold. Customer `add` still hard-fails compatibility facts observable from exact stable Provider aliases and the requested registry graph, and discloses unprovable requirements rather than treating them as satisfied.
- Agreed schema boundary: an ordinary item without `meta.nextHydra` remains a standard ShadCN registry item and uses ShadCN's published `registry-item.json` schema. Only a Selection Definition containing `meta.nextHydra` uses the Next Hydra registry-item schema. That author-facing schema combines the ShadCN registry shape supported by the current CLI with a reusable Next Hydra metadata schema; no second item schema is introduced in v1. Contextual rules such as explicit safe workspace-root targets remain CLI validation performed while building the Composition Plan.
- Agreed metadata ownership: `meta.nextHydra` is strict and rejects unknown fields so misspelled or unsupported composition instructions fail validation. The surrounding standard ShadCN `meta` object remains open, allowing unrelated tools to own their own keys without Next Hydra interpreting or rejecting them.
- Agreed schema evolution: v1 follows ShadCN's latest-schema model. Selection Definitions point to one stable, unversioned Next Hydra schema URL and do not carry `schemaVersion` inside `meta.nextHydra`. Each CLI release bundles its matching runtime validator; an older CLI that cannot validate current metadata fails before materialization and directs the user to run the latest CLI. Explicit schema generations are deferred until Next Hydra has a concrete need to support multiple metadata formats concurrently.
- Agreed Registry Artifact addressing: Next Hydra accepts and preserves the registry address forms supported by ShadCN. Named items and URLs may float to their current content; authors may use a tag, commit SHA, or immutable URL when they need reproducibility. Presets retain the exact addresses chosen by their author, official current presets may reference current named items, and v1 adds no separate Registry Artifact version field or mandatory pinning policy.
- Agreed Provider Alias compatibility: v1 assigns no independent version number to the `@repo/cms`, `@repo/auth`, or `@repo/commerce-provider` package interfaces. The current Baseline imports and Provider exports are the contract. Official Providers and Add-ons are recomposed and typechecked against that contract in CI, while Compatibility Declarations continue to name concrete Selection IDs. A private item receives no stronger source-compatibility guarantee from its metadata; stale code may surface an install or compilation failure that the developer repairs in place. Interface generations are deferred until an independently evolving provider ecosystem creates a concrete need to support old and new contracts concurrently.

## Answer

V1 does not create a version system for composed workspaces. Selection Definitions have stable Selection IDs but no versions; Compatibility Declarations continue to require or conflict with concrete Selection IDs rather than version ranges. Composition Plans are derived afresh for each command, never persisted, and therefore not versioned. Provider Alias interfaces are the current package contracts exercised by the Baseline's real imports, with official Providers and Add-ons recomposed and typechecked against them in CI rather than assigned interface-version numbers.

Next Hydra follows ShadCN's current-schema model. Ordinary items use ShadCN's registry-item schema. Selection Definitions containing `meta.nextHydra` point to one stable, unversioned Next Hydra schema URL that combines the ShadCN item shape supported by the current CLI with strict Next Hydra metadata. Unknown keys inside `meta.nextHydra` fail validation, while unrelated keys in the surrounding `meta` object remain valid. Each CLI bundles its matching runtime validator; an older CLI that cannot understand current metadata stops before materialization and directs the user to run the latest CLI. Explicit schema generations remain a future option only if multiple formats must be supported concurrently.

Registry Artifact identity and reproducibility remain properties of the ShadCN address. Named items and URLs may float, while authors may use tags, commit SHAs, or immutable URLs when they require a fixed artifact. Presets preserve their authors' exact addresses. V1 adds no artifact version field, mandatory pinning, CLI compatibility range, or coupling among CLI, starter, and registry releases. Normal usage runs `create-next-hydra@latest`; explicit CLI pins and starter refs remain debugging and reproduction tools.

A Customer Workspace retains no original Next Hydra or CLI version and has no project-upgrade operation. `add` installs the specifically requested artifact, inspects the complete intact registry graph, current target paths, dependencies, and exact stable Provider aliases, reports conflicts and unknown compatibility assumptions, and leaves any resulting repair work to the developer. It cannot claim that the modified workspace as a whole matches a known Next Hydra release. Full desired-composition validation remains limited to the Maintainer Workspace and the closed-world initial scaffold.
