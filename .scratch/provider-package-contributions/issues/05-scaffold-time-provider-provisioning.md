# Decide how providers and add-ons plug in

Type: grilling
Status: resolved
Blocked by: 04

## Question

Given the earlier research, Next.js constraints, provider and add-on model, and provider-switching prototype, how should providers and add-ons plug into the maintainer repository?

Decide the source-of-truth boundary among provider bundles, add-ons, resolver or CLI discovery, and application composition; choose the generated-adapter, dispatcher, or hybrid mechanism; identify declarative inputs versus derived outputs; and define the smallest common contract that preserves distinct provider seams without forcing false symmetry.

## Comments

- Agreed maintainer workflow: the ordinary cloned Next Hydra repository is the Maintainer Workspace; a second disposable checkout is not required. The repository has a runnable Reference Composition, while Provider switching changes the selection in place and replaces only explicitly targeted Provider-owned application files. A Reference Composition is not a preferred Provider or necessarily a scaffold default.
- Agreed source split: Provider implementation code remains ordinary canonical source. Cross-application files such as Next.js routes are canonical registry source under the Provider's colocated `registry/` directory and are copied to their final targets for the active composition. A developer edits the route source there and runs registry sync before applying or checking the composition.
- Agreed Add-on authoring: registry metadata is colocated with canonical development source. A top-level Add-on uses standard `registryDependencies` for any inseparable frontend, backend, or sidecar items. Each file keeps a source path relative to its colocated registry and declares its final workspace-root target, so maintainers do not copy code into a second canonical registry folder.
- Agreed execution boundary: v1 Provider and Add-on definitions are declarative only. They may declare compatibility, standard registry dependencies and files, typed package dependency or alias changes, and setup instructions. Provider-supplied shell commands, JavaScript hooks, and other arbitrary executable operations are excluded; new needs must earn a specific typed operation. Next Hydra alone validates and executes the Composition Plan.
- Agreed Reference Composition output: its selected application files are committed. A fresh clone is runnable and the copied routes are reviewable; CI checks them against the selected registry sources. A local Provider switch intentionally changes those tracked application files, package manifests, and the lockfile, and switching back restores the Reference Composition. Scaffold-time composition occurs before the customer repository's initial commit.
- Customer-add research: [ShadCN file-target and conflict behavior](../research/03-shadcn-file-conflict-behavior.md) confirms that ShadCN uses resolved target paths and prospective content rather than an ownership receipt: missing files are created, identical files are skipped, changed files require explicit overwrite, and no general removal lifecycle exists.
- Agreed Customer Workspace boundary: scaffold output retains no composition receipt, registry authoring source, or ownership ledger. A later Additive Installation follows the ShadCN target-path/content model: disclose every file, package entry, and other ShadCN-managed effect; create missing targets; skip identical targets; and require either an explicit per-file decision or `--overwrite` for changed targets. `--yes` controls prompting separately and can be combined with `--overwrite` for intentional non-interactive replacement. It does not prove the workspace's Provider ancestry, reconcile a desired composition, or remove code. It hard-fails requirements that can be checked from the exact stable Provider aliases in the current workspace and from Selection Definitions in the requested graph, and explicitly discloses requirements or conflicts that cannot be proven without retained customer composition state.
- Agreed selection-state boundary: a checked-in Workspace Selection is authoritative only inside the Maintainer Workspace and drives repeatable composition and drift checks. Scaffold choices exist while composing the staged project, but `create-next-hydra` removes the Workspace Selection before ownership transfer; the Customer Workspace receives materialized code without retained desired-composition state.
- Agreed Baseline boundary: the Baseline remains ordinary canonical starter-repository source rather than one giant registry item. ShadCN registry items represent all variable Provider and Add-on contributions, including their application route files; `create-next-hydra` combines them with the Baseline.
- Agreed `meta.nextHydra` boundary: a top-level Selection Definition contains only its stable Selection ID, kind and optional Provider Slot, compatibility declarations, and unavoidable exact package requirements or aliases. Files, nested registry dependencies, ordinary npm dependencies, environment placeholders, styling, and documentation remain standard ShadCN fields. The extension has no route language, generic patches, hooks, ownership ledger, or duplicate source-distribution model.
- Agreed target boundary: every copied file declares an explicit `~/...` target relative to the final workspace root. Next Hydra invokes ShadCN once at that root and does not maintain semantic root names, per-item working directories, path overrides, or a persistent root-mapping file.
- Agreed package-manifest semantics: typed requirements compare individual dependency entries rather than replacing whole manifests. A closed-world maintainer composition may set aliases and remove entries declared only by the previous selection. Customer Additive Installation proposes missing entries, skips identical specifications, treats differing specifications as explicit conflicts, and never removes dependencies.
- Corrected failure boundary: maintainer composition does not promise rollback. The CLI preflights known conflicts, stops at the failing operation, exits unsuccessfully, and reports completed and pending work. The developer owns the resulting workspace diff and may repair it or retry; deterministic operations make retry useful without pretending the switch is atomic.
- Agreed route boundary: Providers and Add-ons contribute complete Next.js `route.ts` files through standard ShadCN file entries. The target fixes the public application path and the source file may export any supported methods or implementation needed at that path. Two different files targeting the same route are an ordinary file-target conflict; Next Hydra does not invent a separate method-merging language.
- Agreed route-path boundary: each public route path is fixed by its registry file target in v1. The Workspace Selection does not mount, prefix, or override it. Multiple selected contributions that need the same target remain a future composition problem rather than adding an unused indirection now.
- Revised shared-file boundary: the Baseline continues to own shared application composition files such as `proxy.ts`, `env.ts`, and runtime setup, but it imports selected Providers through stable per-slot package aliases instead of generated binding modules. CMS keeps `@repo/cms`; Auth gains `@repo/auth`; Commerce keeps its provider-neutral `@repo/commerce` module and gains a separate selected-implementation alias such as `@repo/commerce-provider`. Each slot has its own small package interface. Required exports are always present and may deliberately be no-ops when that is valid Provider behavior, so callers do not branch on optional exports. Provider-specific route files import through the same aliases.
- Agreed alias verification: the Baseline's real imports define each Provider Alias interface, and CI recomposes and typechecks the affected applications against every supported Provider. Next Hydra does not add a separate contract package that duplicates those imports. Provider-local tests may verify deliberate no-op behavior, while application compilation catches missing subpaths, incompatible exports, and invalid server or client usage.
- Agreed application import rule: Provider-owned route files and other application-facing contributions import through the selected slot's Provider Alias rather than the concrete Provider package name. A stale contribution therefore fails against the newly selected package instead of continuing to resolve an inactive concrete package that still exists in the Maintainer Workspace. Provider implementation code may use its own concrete or internal imports, and a Provider-specific Add-on relies on both the alias and a concrete compatibility requirement.
- Agreed maintainer source rule: switching the active composition never removes canonical Provider, Add-on, sidecar, or registry source from the Maintainer Workspace. It changes active alias and dependency entries and replaces only the known application targets declared under Provider-local registry source. Customer scaffolding separately includes only the selected Registry Artifacts and does not ship inactive implementations or registry authoring source.

## Answer

Provider selection uses stable package aliases rather than generated binding modules or a runtime dispatcher. The Baseline imports CMS through `@repo/cms`, Auth through `@repo/auth`, and the selected Commerce implementation through `@repo/commerce-provider`; the provider-neutral Commerce domain remains `@repo/commerce`. Each slot owns a small package interface defined by the Baseline's real imports. Required exports are always present, although a Provider may deliberately implement one as a no-op when no behavior is valid, as Drupal already does for its CMS proxy. CI switches each supported Provider into the real applications and typechecks them instead of maintaining a duplicate contract package.

Providers and Add-ons remain self-describing top-level ShadCN registry items. Standard ShadCN fields continue to own copied files, nested items, ordinary npm dependencies, environment placeholders, styling, documentation, registry transport, and normal file-conflict behavior. `meta.nextHydra` adds only composition data: stable Selection ID, kind and optional Provider Slot, concrete-ID requirements and conflicts, and exact package dependency or alias requirements. Files name final workspace-root targets; a package requirement names its `cwd`, dependency section, package name, and exact specifier.

Routes are complete Provider-owned registry files with fixed final application targets. Their normal Next.js source can export multiple HTTP methods, re-export one handler under multiple methods, or reuse the same package handler from different route files. ShadCN copies them like every other text file, and two selected contributions with different contents at the same target conflict before installation. There is no shared catch-all dispatcher, path override, or separate route-description language.

Shared application files such as `proxy.ts`, `env.ts`, and Effect runtime composition remain Baseline-owned source and use the stable aliases. Provider-specific standalone source can still be a normal ShadCN contribution. Selection definitions contain no executable hooks, generic patch language, ownership ledger, or rollback promise; a new mutation must earn a specific declarative operation.

The ordinary repository is the Maintainer Workspace. All canonical Provider, Add-on, sidecar, and registry source remains present so maintainers can edit it directly. Its checked-in Workspace Selection chooses the active aliases, dependencies, Add-ons, and application files, and CI checks that committed managed application files match the selected registry sources. Switching changes tracked manifests, routes, and the lockfile and may run one workspace install. On failure, the command stops, reports completed and pending work, and leaves the Git diff for the developer to repair or retry.

A Customer Workspace receives the Baseline plus only the selected Registry Artifacts and aliases. Routes are already part of those artifacts. It receives no Workspace Selection, registry source, receipt, or ownership ledger. A later Additive Installation walks the intact dependency graph before ShadCN flattens it, rejects conflicting target claims, shows proposed files, package entries, and other ShadCN-managed effects, creates missing files, skips identical files, and requires per-file approval or an explicit `--overwrite` for changed targets. It checks exact known Provider aliases and discloses compatibility assumptions it cannot prove. It never infers permission to remove customer-owned code.
