# Decide how providers and add-ons plug in

Type: grilling
Status: resolved
Blocked by: 04

## Question

Given the earlier research, Next.js constraints, provider and add-on model, and provider-switching prototype, how should providers and add-ons plug into the maintainer repository?

Decide the source-of-truth boundary among provider bundles, add-ons, resolver or CLI discovery, and application composition; choose the generated-adapter, dispatcher, or hybrid mechanism; identify declarative inputs versus derived outputs; and define the smallest common contract that preserves distinct provider seams without forcing false symmetry.

## Comments

- Agreed maintainer workflow: the ordinary cloned Next Hydra repository is the Maintainer Workspace; a second disposable checkout is not required. The repository has a runnable Reference Composition, while provider switching changes the selection in place and regenerates only explicitly derived application glue. A Reference Composition is not a preferred Provider or necessarily a scaffold default.
- Agreed source split: Provider implementation code remains ordinary canonical source and generated application adapters remain mechanical output. A developer edits the Provider implementation directly; only route-shape changes require regenerating the application adapter.
- Agreed Add-on authoring: each Install Unit's registry metadata is colocated with its canonical development source. A top-level Add-on references its root-scoped Install Units, while a root registry may include or index their definitions. ShadCN builds distributable Registry Artifacts by reading and inlining those source files; maintainers do not copy them into a second canonical registry folder.
- Agreed execution boundary: v1 Provider and Add-on definitions are declarative only. They may declare compatibility, root-scoped Install Units, generated Next.js route exports, typed package dependency or alias changes, and setup instructions. Provider-supplied shell commands, JavaScript hooks, and other arbitrary executable operations are excluded; new needs must earn a specific typed operation. Next Hydra alone validates and executes the Composition Plan.
- Agreed Reference Composition output: its Generated Adapters are committed. A fresh clone is runnable and the generated glue is reviewable; CI checks it against the resolved Composition Plan. A local Provider switch intentionally changes those tracked adapters, package manifests, and the lockfile, and switching back restores the Reference Composition. Scaffold-time composition occurs before the customer repository's initial commit.
- Customer-add research: [ShadCN file-target and conflict behavior](../research/03-shadcn-file-conflict-behavior.md) confirms that ShadCN uses resolved target paths and prospective content rather than an ownership receipt: missing files are created, identical files are skipped, changed files require explicit overwrite, and no general removal lifecycle exists.
- Agreed Customer Workspace boundary: scaffold output retains no composition receipt, registry authoring source, or ownership ledger. A later Additive Installation follows the ShadCN target-path/content model: disclose every file and package change, create missing targets, skip identical targets, and require an explicit per-file decision for changed targets. It does not prove the workspace's Provider ancestry, reconcile a desired composition, remove code, or use a global overwrite authorization. Compatibility requirements remain hard in closed-world maintainer/scaffold Composition Plans; customer Additive Installation discloses relevant assumptions without pretending to know the complete modified stack.
- Agreed selection-state boundary: a checked-in Workspace Selection is authoritative only inside the Maintainer Workspace and drives repeatable composition and drift checks. Scaffold choices exist while composing the staged project, but `create-next-hydra` removes the Workspace Selection before ownership transfer; the Customer Workspace receives materialized code without retained desired-composition state.
- Agreed Baseline boundary: the Baseline remains ordinary canonical starter-repository source rather than one giant registry item. ShadCN registry items represent variable Provider and Add-on contributions; `create-next-hydra` combines them with the Baseline and Generated Adapters.
- Agreed `meta.nextHydra` boundary: a top-level Selection Definition contains only schema version, stable Selection ID, kind and optional Provider Slot, compatibility declarations, root-scoped Install Unit references, generated Next.js route declarations, and unavoidable exact package requirements or aliases. Files, nested registry dependencies, ordinary npm dependencies, environment placeholders, styling, and documentation remain standard ShadCN fields. The extension has no generic patches, hooks, ownership ledger, or duplicate source-distribution model.
- Agreed Install Unit roots: v1 uses validated workspace-relative `cwd` paths, with `.` for the workspace root. It does not introduce semantic root names or a persistent root-mapping file. A modified Customer Workspace may provide an explicit path override when the declared root no longer exists.
- Agreed package-manifest semantics: typed requirements compare individual dependency entries rather than replacing whole manifests. A closed-world maintainer composition may set aliases and remove entries declared only by the previous selection. Customer Additive Installation proposes missing entries, skips identical specifications, treats differing specifications as explicit conflicts, and never removes dependencies.
- Corrected failure boundary: maintainer composition does not promise rollback. The CLI preflights known conflicts, stops at the failing operation, exits unsuccessfully, and reports completed and pending work. The developer owns the resulting workspace diff and may repair it or retry; deterministic operations make retry useful without pretending the switch is atomic.
- Agreed route boundary: Providers and Add-ons declare their Next.js Route Handlers as URL-path and HTTP-method mappings to exported package handlers. Next Hydra merges distinct methods for the same path into one generated `route.ts`; the generated file is derived application glue, not Provider-owned source. A duplicate claim for the same normalized path and method is a conflict instead of an implicit composition rule.
- Agreed route-path boundary: each public route path is fixed by its registry declaration in v1. The resolver validates the declared paths and methods but does not mount, prefix, or override them from the Workspace Selection. Multiple selected Providers that need the same path remain a future composition problem rather than adding an unused indirection now.
- Revised shared-file boundary: the Baseline continues to own shared application composition files such as `proxy.ts`, `env.ts`, and runtime setup, but it imports selected Providers through stable per-slot package aliases instead of generated binding modules. CMS keeps `@repo/cms`; Auth gains `@repo/auth`; Commerce keeps its provider-neutral `@repo/commerce` module and gains a separate selected-implementation alias such as `@repo/commerce-provider`. Each slot has its own small package interface. Required exports are always present and may deliberately be no-ops when that is valid Provider behavior, so callers do not branch on optional exports. Provider-specific routes remain Generated Adapters because package aliases cannot create Next.js filesystem routes.
- Agreed alias verification: the Baseline's real imports define each Provider Alias interface, and CI recomposes and typechecks the affected applications against every supported Provider. Next Hydra does not add a separate contract package that duplicates those imports. Provider-local tests may verify deliberate no-op behavior, while application compilation catches missing subpaths, incompatible exports, and invalid server or client usage.
- Agreed application import rule: Generated Adapters and other application-facing Provider contributions import through the selected slot's Provider Alias rather than the concrete Provider package name. A stale generated contribution therefore fails against the newly selected package instead of continuing to resolve an inactive concrete package that still exists in the Maintainer Workspace. Provider implementation code may use its own concrete or internal imports, and a Provider-specific Add-on relies on both the alias and a concrete compatibility requirement.
- Agreed maintainer source rule: switching the active composition never removes canonical Provider, Add-on, or sidecar source from the Maintainer Workspace. It changes active alias and dependency entries and regenerates only derived application glue. Customer scaffolding separately includes only the selected Registry Artifacts and does not ship inactive implementations or registry authoring source.

## Answer

Provider selection uses stable package aliases rather than generated binding modules or a runtime dispatcher. The Baseline imports CMS through `@repo/cms`, Auth through `@repo/auth`, and the selected Commerce implementation through `@repo/commerce-provider`; the provider-neutral Commerce domain remains `@repo/commerce`. Each slot owns a small package interface defined by the Baseline's real imports. Required exports are always present, although a Provider may deliberately implement one as a no-op when no behavior is valid, as Drupal already does for its CMS proxy. CI switches each supported Provider into the real applications and typechecks them instead of maintaining a duplicate contract package.

Providers and Add-ons remain self-describing top-level ShadCN registry items. Standard ShadCN fields continue to own copied files, nested items, ordinary npm dependencies, environment placeholders, styling, documentation, registry transport, and normal file-conflict behavior. `meta.nextHydra` adds only composition data: schema version, stable Selection ID, kind and optional Provider Slot, concrete-ID requirements and conflicts, root-scoped Install Unit references, exact package dependency or alias requirements, and Next.js route declarations. An Install Unit names a registry item and a validated workspace-relative `cwd`; a package requirement names its `cwd`, dependency section, package name, and exact specifier.

Routes are fixed registry declarations mapping one public URL path and one or more supported HTTP methods to named exports from the selected Provider Alias. Next Hydra reduces them to path-and-method claims, rejects duplicate claims, and generates the exact application-owned `route.ts` files. The same handler may serve any number of methods or paths. There is no shared catch-all dispatcher, path override, arbitrary route code, or automatic composition of two handlers claiming the same method and path.

Shared application files such as `proxy.ts`, `env.ts`, and Effect runtime composition remain Baseline-owned source and use the stable aliases. Provider-specific standalone source can still be a normal ShadCN contribution. Selection definitions contain no executable hooks, generic patch language, ownership ledger, or rollback promise; a new mutation must earn a specific declarative operation.

The ordinary repository is the Maintainer Workspace. All canonical Provider, Add-on, and sidecar source remains present so maintainers can edit it directly. Its checked-in Workspace Selection chooses the active aliases, dependencies, Add-ons, and generated routes, and CI checks that committed generated routes match that selection. Switching changes tracked manifests, routes, and the lockfile and may run one workspace install. On failure, the command stops, reports completed and pending work, and leaves the Git diff for the developer to repair or retry.

A Customer Workspace receives the Baseline plus only the selected Registry Artifacts, aliases, and generated routes. It receives no Workspace Selection, registry source, receipt, or ownership ledger. A later Additive Installation shows proposed files and package changes, creates missing files, skips identical files, and treats changed files as explicit per-file conflicts. It never infers permission to remove or replace customer-owned code.
